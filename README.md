# 规则驱动的分货决策引擎（Rule-based Allocation Engine）

[![CI](https://github.com/Aiden-paradox/rule-allocation-engine/actions/workflows/ci.yml/badge.svg)](https://github.com/Aiden-paradox/rule-allocation-engine/actions/workflows/ci.yml)

![License](https://img.shields.io/badge/license-MIT-green)
![Dependencies](https://img.shields.io/badge/dependencies-0-brightgreen)

一个可直接运行的决策系统小项目：把“老员工凭经验分货”的模糊判断，转化为**清晰、可配置、可验证、可复现**的规则与代码，并输出可审计的分货方案与经营指标。

> 场景灵感来自真实业务：新品预测、渠道分货、库存分配、物流规划等复杂决策问题。项目不依赖任何第三方库，只用 Python 标准库，克隆后即可运行。

## 核心结果

同一批库存、同一组需求，只改规则，得到不同结果——这就是“规则必须显性化、可对比”的证明：

| 指标 | baseline（稳健分配） | growth（倾斜重点渠道） |
| --- | --- | --- |
| 整体满足率 | 63.7% | **67.2%** |
| 最低渠道满足率 | **50.4%** | 44.8% |
| 渠道满足率基尼系数（越小越公平） | **0.0804** | 0.1209 |
| 未满足需求 | 1180 | 1065 |
| 需求预测回测 MAPE | 16.43%（加权移动平均） | 16.43% |

结论：向重点渠道倾斜能提高整体满足率，但会牺牲渠道公平性——这类取舍可以量化、可以讨论，而不是靠“感觉”。

## 一、业务问题

假设你是一家硬件公司负责渠道分货的人，手上有一批库存，渠道需求各不相同：

- 旗舰店不能缺货，但线下经销商也不能长期饿着；
- 电商大促需要提前备货，但库存一旦压死就是现金流风险；
- 老板说“优先保重点渠道”，可“重点”到底值多少？没人说得清。

传统做法依赖个人经验，问题有三个：**规则说不清、结果算不出、方案比不了**。本项目的目标是把这套经验显性化为规则，并用代码给出可复现的分配结果。

## 二、快速开始

```bash
# 1) 无需安装任何依赖，Python 3.9+ 即可
python -m allocation.cli --scenario both --out outputs

# 2) 运行单元测试
python -m unittest discover -s tests -v
```

运行后会在 `outputs/` 目录生成：

| 文件 | 说明 |
| --- | --- |
| `allocation_baseline.csv` | 基线规则下的逐渠道分货结果 |
| `allocation_growth.csv` | 进取规则下的逐渠道分货结果 |
| `forecast.csv` | 基于历史销量的需求预测 |
| `report.md` | 两种规则方案的对比分析报告 |

## 四、规则怎么配置

规则全部写在 JSON 里，业务同学改规则不需要改代码：

```json
{
  "name": "baseline",
  "safety_stock_ratio": 0.10,
  "min_fill_ratio": 0.50,
  "max_share_per_channel": 0.60,
  "priority_weights": { "旗舰店": 3, "电商自营": 2, "线下经销": 2, "新渠道": 1 }
}
```

| 规则 | 业务含义 |
| --- | --- |
| `safety_stock_ratio` | 预留安全库存比例，防止一次性分光 |
| `min_fill_ratio` | 每个渠道的最低保障比例，避免小渠道被饿死 |
| `max_share_per_channel` | 单渠道占比上限，防止一家独大、风险集中 |
| `priority_weights` | 渠道优先级权重，数值越高越优先拿到增量库存 |

## 五、算法流程

1. **数据校验**：库存、需求、规则逐项校验，异常直接报错而不是“悄悄算错”。
2. **预留安全库存**：可分配库存 = 可用库存 × (1 − 安全库存比例)。
3. **第一轮保底**：按优先级排序，先给每个渠道发放最低保障比例。
4. **第二轮增量**：剩余库存按“优先级权重 × 未满足需求”加权分配。
5. **上限约束**：任何渠道不得超过单渠道占比上限。
6. **结果与指标**：输出逐渠道分配结果、满足率、缺口与公平性指标。

## 六、输出指标

| 指标 | 定义 | 业务用途 |
| --- | --- | --- |
| 整体满足率 | 已分配 / 总需求 | 判断库存是否充足 |
| 渠道满足率 | 单渠道已分配 / 单渠道需求 | 判断渠道是否被饿死 |
| 最低渠道满足率 | 所有渠道满足率的最小值 | 衡量公平性风险 |
| 未满足需求 | 总需求 − 已分配 | 缺口暴露 |
| 剩余库存 | 可用库存 − 已分配 | 现金流与再分配空间 |
| 基尼系数 | 渠道满足率分布的不均衡程度 | 量化“分得公不公平” |

## 七、两种规则方案对比

项目内置两套规则，用于回答“规则一变，结果差多少”：

- `baseline`：保底优先、稳健分配；
- `growth`：更激进地倾斜重点渠道与增长渠道。

运行 `--scenario both` 会输出对比报告，量化两套规则在满足率、缺口、公平性上的差异——这正是“规则可验证”的价值。

## 八、设计取舍与局限

- 需求来自历史数据预测，未引入价格、促销、竞品等外部变量；
- 分配算法是规则驱动的启发式方法，不是全局最优的运筹优化；
- 示例数据为小规模演示数据，用于验证逻辑而非真实经营结论。

下一步可扩展：接入真实 ERP/BI 数据、引入库存周转与缺货成本目标函数、用 OR-Tools 求最优解、用大模型辅助把业务访谈转成规则草案。

## 九、为什么做这个项目

这个项目想展示的是把一个模糊的管理问题，拆成**规则、数据、算法、指标**四件可验证的事，并让业务人员能改规则、工程师能跑代码、管理者能看指标。项目作者为材料科学与工程背景，具备 Python 与机器学习项目经验，正在把“数据驱动”的方法从科研迁移到业务决策场景。
