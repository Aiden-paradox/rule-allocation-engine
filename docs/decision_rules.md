# 规则设计说明：把“经验”翻译成“规则”

这个项目最想展示的，是把业务里说不清的判断，变成可写下来、可算出来、可比较的规则。下面是一张“经验 → 规则”的翻译表。

| 业务里的说法（模糊经验） | 翻译后的规则 | 代码位置 | 可验证指标 |
| --- | --- | --- | --- |
| “先把货铺开，别让渠道饿死” | `min_fill_ratio`：每个渠道先拿到最低保障比例 | `engine._allocate_sku` 第一轮 | 最低渠道满足率 |
| “重点渠道要多给点” | `priority_weights`：按权重分配剩余库存 | `engine._allocate_sku` 第二轮 | 各渠道满足率差异 |
| “不能让一家把货吃光” | `max_share_per_channel`：单渠道占比上限 | `engine._allocate_sku` 上限约束 | 单渠道最大占比 |
| “总得留点库存应急” | `safety_stock_ratio`：预留安全库存 | `engine._allocate_sku` | 剩余库存 |
| “这么分到底公不公平？” | 基尼系数衡量渠道满足率不均衡程度 | `metrics._gini` | 渠道满足率基尼系数 |
| “换个分法会差多少？” | 多规则方案对比 | `cli --scenario both` | 两套规则的指标对比 |

## 为什么这样设计

1. **规则与代码分离**：业务同学改 JSON，工程师改代码，避免规则散落在个人经验里。
2. **可验证**：每条规则都对应一个可计算的指标，方案好坏能比较。
3. **可审计**：分配过程分两轮、有明确顺序，出现争议能回溯到规则。
4. **可扩展**：未来把启发式规则换成运筹优化、把预测换成机器学习模型，接口不变。
